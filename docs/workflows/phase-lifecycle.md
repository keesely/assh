# Phase 生命周期工作流

> 本文档抽象了 assh v2.0.0 项目从 Phase 2 到 Phase 5 的实际工作模式，
> 定义了一个 Phase 从启动到关闭的完整生命周期。

## 概览

```
Phase 启动
  │
  ├── Step 1: 现状审查 ────────── 阅读代码/文档，了解上下文
  ├── Step 2: 需求澄清 ────────── 多轮 question，消除歧义
  ├── Step 3: 术语定义 ────────── 统一概念，建立术语表
  ├── Step 4: 架构决策 ────────── 创建/更新 ADR
  ├── Step 5: 方案设计 ────────── 模块设计 + 文件清单 + 接口定义
  ├── Step 6: 文档对齐 ────────── 同步所有关联文档
  ├── Step 7: 代码实现 ────────── 交给 Build Agent
  └── Step 8: 验收闭合 ────────── 验收标准验证 + 合并 + tag
```

---

## Step 1: 现状审查

在开始任何新 Phase 的设计前，先审查已有上下文。

### 检查清单

| 审查项 | 内容 | 目的 |
|--------|------|------|
| `AGENTS.md` | 项目状态、已完成模块、依赖 | 了解当前进度 |
| `docs/TODO.md` | 本 Phase 的原始任务规划 | 了解预期范围 |
| `docs/plan.md` | 技术选型、架构分层 | 参考一致 |
| `docs/adrs.md` | 已做出的架构决策 | 避免冲突 |
| 已有代码 | 已完成模块的源码（domain/port/service/infra） | 了解模式 |
| 旧版代码 | v1 的对应模块（如有） | 参考兼容性 |

### 审查产出

- 当前状态摘要（什么已完成，什么未完成）
- 已有的接口定义和模式（如 repository、service 的构造器注入风格）
- 与本 Phase 的依赖关系矩阵

---

## Step 2: 需求澄清

这是最重要的步骤。未澄清的需求直接进入设计会导致大量返工。

### 方法论

```
逐项聚焦 → 提供选项 → 确认决策 → 记录结论
```

1. **逐项聚焦**：每次只提出一个问题或一组强相关问题
2. **提供选项**：给出 2-3 个候选方案（A/B/C），说明优缺点
3. **确认决策**：用户可能选择其中一个，或提出全新方案
4. **记录结论**：立即记录到 worklog 中

### question 设计规范

```
Q: [场景描述]
  A) [方案A] — [优点] / [缺点]
  B) [方案B] — [优点] / [缺点]
  C) [方案C] — [需额外资源] / [灵活]
```

### 澄清轮次

从 Phase 2~5 的统计：

| Phase | 澄清轮次 | 关键决策数 | 澄清文档行数 |
|-------|----------|-----------|-------------|
| Phase 2 | 3 轮 | 3（SQLite/静态密钥/AuthService推迟） | 303 |
| Phase 3 | 2 轮 | 5（接口粒度/Agent/HostKey/Keepalive/Service层） | 148 |
| Phase 4 | 6 轮 | 6（密码输入/直连格式/bc输出/Options/路径/参数对齐） | 138 |
| Phase 5 | 7 轮 | 8（进度格式/批量行为/路径创建/Glob/交互命令/续传/并发） | 103 |

### 关键原则

- **至少 2-3 轮澄清**：第一轮往往是用户直觉回答，后续轮次会暴露出细节矛盾
- **争议必须完全消除**：所有"待确认"事项清零后再进入设计
- **边界案例必须覆盖**：如 Phase 5 的"远程文件比本地大，续传不可用"边界
- **确认后在文档中标记决策**：使用 `✅` 标记已确认

## Step 3: 术语定义

在架构设计前，**先统一关键术语**。这一点从 Phase 4 起开始系统化使用。

### 方法

```
识别歧义词 → 定义精确含义 → 写入术语表 → 全体对齐
```

### 典型的歧义术语

| 术语 | 可能歧义 | 本项目的精确定义 |
|------|----------|-----------------|
| server | 服务进程/机器/配置条目 | 配置中保存的 SSH 目标（域名/IP+端口+用户+认证） |
| login | 登录/连接/打开 shell | 建立交互式 SSH Shell 会话 |
| session | ssh 会话/REPL | 单个 ssh.Client 上的 Shell/Run 操作 |
| push | 推送/上传 | 从本地传输到远程服务器 |
| pull | 拉取/下载 | 从远程服务器传输到本地 |
| resume | 续传/断点续传 | 从文件中断位置继续，不重复已传输部分 |

### 术语定义时机

- 在 Step 2（需求澄清）中**发现歧义时立即定义**
- 在 `docs/glossary.md` 或模块文档开头维护

## Step 4: 架构决策（ADR）

每个重大架构决策必须记录。详见 [document-management.md](document-management.md) 的 ADR 章节。

### Phase 的 ADR 产出统计

| Phase | 新增 ADR | 主要决策内容 |
|-------|----------|-------------|
| Phase 0 | ADR-001~003 | 三层架构、目录设计、DI 策略 |
| Phase 1 | ADR-004~007 | crypto 位置、日志处理 |
| Phase 2 | ADR-008~010 | SQLite、AES-GCM、AuthService 推迟 |
| Phase 3 | ADR-011 | SSH 连接层架构 |
| Phase 4 | ADR-012~016 | CLI 参数/版本管理/命令架构 |
| Phase 5 | ADR-017~019 | SFTP 架构/known-servers/Hash Header |

### ADR 触发条件

1. 新技术栈引入
2. 不兼容变更（API/数据格式/协议）
3. 架构模式调整（分层/模块拆分/合并）
4. 安全与合规决策
5. 核心流程重构（涉及 ≥ 3 个模块）

---

## Step 5: 方案设计

需求澄清 + 架构决策完成后，进入详细设计。

### 设计产出

| 产出物 | 内容 | 示例 |
|--------|------|------|
| 模块设计文档 | `docs/modules/<name>.md` | 接口定义、数据流、文件清单 |
| TODO 任务表 | `docs/TODO.md` 中本 Phase 的章节 | 子任务列表、文件路径、状态 |
| 验收标准 | `docs/TODO.md` 中的验收清单 | F1~F21 验收场景表 |
| 文件清单 | 需要创建和修改的文件列表 | 含说明和状态列 |

### 设计文档结构

```markdown
## 概述
- 功能范围
- 依赖关系

## 接口设计
- port 层接口定义
- 关键方法签名
- 数据结构

## 实现方案
- 模块结构
- 数据流图
- 边界处理

## 文件清单
| 文件 | 说明 | 状态 |

## 验收标准
| # | 场景 | 操作 | 预期 |
```

## Step 6: 文档对齐

设计完成后，**所有相关文档同步更新**。这是最容易被忽略但最重要的一步。

### 对齐检查清单

| 文档 | 对齐触发条件 |
|------|-------------|
| `AGENTS.md` | Phase 状态变化、技术栈变更 |
| `docs/TODO.md` | 任务增减、范围变化、验收标准 |
| `docs/plan.md` | 技术选型、项目结构变更 |
| `docs/adrs.md` | ADR 新增/状态变更 |
| `docs/adrs/<N>-标题.md` | 新 ADR 或修改 |
| `docs/architecture.md` | 架构图/数据流变更 |
| `docs/constraints.md` | 依赖/约束变化 |
| `docs/storage.md` | 存储路径/数据结构变化 |
| `docs/modules/<name>.md` | 对应模块设计变更 |
| `docs/requirements/` | 需求状态变化 |

### 对齐原则

- **批量更新**：所有文档在同一批次中更新，而不是分散提交
- **从核心到边缘**：先更新核心计划文档（TODO.md/plan.md），再更新模块文档
- **交叉引用检查**：更新后 grep 搜索所有被修改的 Phase 编号、文件名引用
- **ADR 索引同步**：新增 ADR 后立即更新 `docs/adrs.md` 统计数和列表

---

## Step 7: 代码实现

设计完成后交给 Build Agent 进行编码实现。

### 交接清单

| 交接项 | 内容 |
|--------|------|
| TODO 任务表 | 每个任务的优先级和依赖 |
| 接口定义 | port 层接口签名 |
| 验收标准 | F1~F{N} 的具体验收场景 |
| 文件清单 | 哪些文件新建/修改 |
| 测试要求 | 单元测试覆盖率、Mock 模式 |

### Build Agent 工作规范

- 必须遵循 port/service/infra 三层架构
- 先在 port 层定义接口，再在 infra 层实现
- 构造器注入，组合根在 main.go
- TDD：先写测试再写实现
- 每次修改后执行 `go build ./...` 确保护编译

---

## Step 8: 验收闭合

### 验收流程

```
实现完成 → 执行验收标准 → 修复问题 → 全部通过 → 打 tag → 合并
```

### 验收标准执行

1. 对照 TODO.md 中的验收清单（F1~F{N}）逐项验证
2. 使用 `test` 和 `question` 验证功能
3. 全部通过后更新验收检查项状态为 ✅

### 分支合并流程

```bash
# 1. 确保当前 Phase 分支最新
git checkout dev/v2.0.0-phase-N
git pull origin dev/v2.0.0-phase-N

# 2. 合并到 master（使用 git-manager skill）
git checkout master
git merge --no-ff dev/v2.0.0-phase-N

# 3. 打 tag
git tag -a v2.0.0-phase-N -m "Phase N complete: <描述>"

# 4. 推送
git push origin master --tags
```

### 闭合产出

| 产出 | 说明 |
|------|------|
| Phase 闭合报告 | 记录在 worklog 中，包含成果/问题/遗留项 |
| git tag | `v2.0.0-phase-N` |
| AGENTS.md 状态更新 | Phase N → ✅ 完成 |
| 下一个 Phase 分支已创建 | `dev/v2.0.0-phase-(N+1)` |

## 实验阶段（Phase X）的工作流

实验阶段使用简化流程：

```
需求提出 → 快速原型 → 用户确认 → 或升级为正式 Phase / 或废弃
```

- 不需要完整的 ADR 和文档对齐
- 不纳入分支管理（可在 feat/ 分支上实验）
- 验收标准简化
