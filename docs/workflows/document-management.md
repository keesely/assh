# 文档管理与对齐工作流

> 本文档定义项目文档的分类体系、创建流程、更新触发条件和对齐约束。
> 基于 Phase 2~5 的实际文档操作经验抽象而成。

## 文档分类

### 核心计划文档（修改频率：阶段级）

| 文档 | 作用 | 更新触发 |
|------|------|----------|
| `AGENTS.md` | 项目全局状态看板 | Phase 状态变更、技术栈变更 |
| `docs/TODO.md` | 任务清单 + 验收标准 | Phase 启动/设计变更/范围调整 |
| `docs/plan.md` | 技术选型 + 项目结构 | 架构变更、依赖变更 |

#### 更新顺序约束

```
AGENTS.md  ←  全局状态（最先更新）
   ↓
plan.md    ←  技术层面（第二顺位）
   ↓
TODO.md    ←  任务层面（最后更新，依赖前两者的确认）
```

### 架构决策记录（修改频率：事件级）

| 文档 | 作用 | 更新触发 |
|------|------|----------|
| `docs/adrs.md` | ADR 索引 | ADR 新增/状态变更 |
| `docs/adrs/<N>-<标题>.md` | 具体决策 | 重大架构决策 |

#### ADR 创建流程

```
1. 识别触发条件（见下方触发条件清单）
2. 确定 ADR 编号（检查 adrs.md 列表，确保无冲突）
3. 使用 adrs-manager skill 或手动创建文件
4. 遵循 ADR 模板：
   - Status / Date / Context / Decision / Consequences / Related
5. 更新 docs/adrs.md 索引（统计数 + 列表 + 摘要）
6. 在相关文档中引用 ADR 编号
```

#### ADR 编号规范

- **格式**：`XXX`（3 位，从 001 开始，连续递增）
- **禁用**：跳过编号、复用已废弃编号、编号重排
- **命名**：`<N>-<中文标题>.md`，短横线分隔
- **冲突处理**：发现冲突时，检查历史记录确认真实编号，修改文件名而非重新编号

#### ADR 触发条件

| 类型 | 触发场景 | 必须创建 | 示例 |
|------|----------|----------|------|
| 新技术栈 | 引入数据库/中间件/新库 | ✅ | ADR-008: SQLite |
| 不兼容变更 | 数据格式/API/协议变更 | ✅ | ADR-009: AES-GCM |
| 模式调整 | 分层/模块拆分合并 | ✅ | ADR-017: 二进制拆分 |
| 安全决策 | 加密/认证/隐私变更 | ✅ | ADR-009, ADR-019 |
| 重构 ≥3 模块 | 核心流程重构 | ✅ | ADR-011: SSH 连接层 |
| UX 增强 | 不影响架构的输出格式优化 | ❌ | ADR-015 可选 |
| Bug 修复 | 不影响接口的修复 | ❌ | 记录在 bugs.md |

### 模块文档（修改频率：设计级）

| 文档 | 作用 | 创建/更新时机 |
|------|------|---------------|
| `docs/modules/<name>.md` | 模块详细设计 | Phase 设计期间 |
| `docs/storage.md` | 存储路径和结构 | 数据结构变更时 |
| `docs/architecture.md` | 架构图/数据流 | 架构变更时 |
| `docs/constraints.md` | 约束/依赖 | 新增依赖时 |

#### 模块文档模板

```markdown
# <模块名>

## 概述
- 功能范围
- 输入/输出
- 依赖关系

## 接口定义
- port 层接口签名
- 关键数据结构

## 实现方案
- 文件结构
- 数据流
- 边界处理

## 文件清单
| 文件 | 职责 | 状态 |
```

### 需求文档（修改频率：事件级）

| 文档 | 作用 | 更新时机 |
|------|------|----------|
| `docs/requirements/README.md` | 需求索引 + 元数据规范 | 新增/状态变更 |
| `docs/requirements/RQ-<N>.md` | 具体需求 | 用户提出/排期/实现 |

**状态流转**：
```
proposed → clarifying → accepted → in_progress → implemented
                    ↘ rejected
                    ↘ deferred
```

### 工作报告（记录级）

| 文档 | 作用 | 更新时机 |
|------|------|----------|
| `docs/worklogs/<date>-<title>.md` | 分析/设计/决策完整流程 | 每个工作会话结束 |

#### 工作报告模板

```markdown

> 日期: YYYY-MM-DD
> 分支: <branch>
> 状态: <status>

---

## 1. 工作概览

| 阶段 | 步骤 | 成果 |
|------|------|------|

(最终方案、接口定义、文件清单)

```

## 文档对齐约束

### 约束规则

1. **跨文档一致性**：同一信息（如 Phase 编号、文件名、接口签名）在不同文档中必须一致
2. **更新原子性**：一次设计变更导致的文档修改必须一次性提交，不拆散到多个 commit
3. **引用有效性**：所有跨文件引用（如 `[xxx](path/to/file.md)`）必须可访问
4. **反向同步**：修改核心文档后，检查哪些边缘文档引用了该信息并同步更新

### 对齐检查流程

```
修改完成 → 执行 grep 扫描 → 修复冲突 → 最终确认
```

#### grep 扫描清单

```bash
# 1. 扫描 Phase 编号引用
rg 'Phase [0-9]+' docs/ --type md

# 2. 扫描 ADR 引用
rg 'ADR-[0-9]+' docs/ --type md

# 3. 扫描文件名引用
rg 'asshv2/[\w/.-]+' docs/ --type md

# 4. 扫描接口/函数名引用
rg 'func \w+' docs/modules/ --type md
```

### 历史文档处理

工作日志（`docs/worklogs/`）和历史 ADR 中记录的旧信息**不追溯修改**：

| 场景 | 处理方式 |
|------|----------|
| Phase 编号变动 | 旧 Phase 编号保留在工作日志中（历史上下文） |
| ADR 重命名 | 保留原名作为历史记录，通过 `adrs.md` 索引维护一致性 |
| 已废弃决策 | 在 ADR 中标记 `status: deprecated` 并注明替代方案 |
| 旧版本文件 | `assh/` 和 `backup/` 目录禁止修改，仅可阅读 |

## 元数据规范

所有需求文档和正式文档建议包含 YAML front matter：

```yaml
---
id: RQ-001              # 唯一编号
title: 简短标题          # 一行概述
status: proposed        # 状态
created: 2026-05-10     # 创建日期
updated: 2026-05-10     # 最后更新
phase: none             # 计划阶段
related_adr: []         # 关联 ADR
tags: [cli, ux]         # 标签
---
```
