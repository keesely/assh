# 抽象复盘与可复用经验

> 本文档基于 Phase 2~5 的实际项目经验，抽象出通用工作模式和反模式。
> 适用于 PM Agent 在新项目中复用，也作为当前项目的经验沉淀。

---

## 一、经验黄金法则

### 法则 1：需求澄清永远不够多

**观察**：Phase 2 只做了 3 轮澄清，结果在实现中出现了细节歧义（如加密引擎的 CGO 限制）。
Phase 5 做了 7 轮澄清，虽然前期投入大，但实现阶段几乎没有设计层面的返工。

**规律**：澄清轮次与实现阶段的返工率呈反比。

**做法**：
- 每轮澄清聚焦 1-2 个主题，深度讨论
- 覆盖主流、边界、异常三种场景
- 记录每个确认的决策和理由
- 全部确认后才进入设计阶段

### 法则 2：文档对齐必须显式检查

**观察**：Phase 2~4 的文档对齐基本正确，但 Phase 5 的 ADR 编号冲突（017 重复）和 Phase 编号位移遗漏（ADR-017 中 Phase 10→11 mount 引用修复），都是因为"想当然以为对了"——没有显式 grep 检查。

**做法**：
- 设计完成后，强制执行 grep 扫描（见 document-management.md 的扫描清单）
- 不要依赖"我记得更新了"，而是依赖"我 grep 确认了"
- ADR 文件列表必须手动逐行检查连续性

### 法则 3：术语在第一天定义

**观察**：Phase 3 中 "session" 一词被同时用作 "SSH session" 和 "交互式终端会话"，需要额外澄清。Phase 4 开始在 `question` 中同步定义术语，效率更高。

**做法**：
- 需求澄清阶段，遇到模糊术语立即定义
- 术语定义写在模块文档开头或独立术语表
- 术语定义一旦确定，全项目统一使用

### 法则 4：验收标准先于代码

**观察**：所有验收标准在 TODO.md 中预定义的 Phase，实现完成后验收流畅。
如果在实现后才补验收标准，容易出现"实现的功能不是用户想要的"情况。

**做法**：
- 验收标准在设计阶段完成，与任务表同时编写
- 每个验收标准包含：场景、操作、预期结果
- 验收标准编号（F1, F2, ...）与验收阶段一一对应
- 开发者实现时以验收标准为通过条件

### 法则 5：worktree 模式的双仓库同步

**观察**：项目使用 `assh-builder/`（配置） + `assh/`（代码 git 仓库） + `asshv2/`（worktree）的三层结构，两个 git 仓库需要独立管理：

| 场景 | assh-builder | asshv2 |
|------|-------------|--------|
| 分支创建 | 同步创建 `dev/v2.0.0-phase-N` | 同步创建同名分支 |
| 设计提交 | 提交设计文档 | 提交 port 接口 |
| 代码提交 | 不涉及 | 提交实现代码 |
| 合并/tag | 同步合并+打 tag | 同步合并+打 tag |

**教训**：两个仓库若不同步，会导致 `asshv2` 在错误的 branch 上。

## 二、反模式清单（已踩的坑）

### 🔴 [Critical] ADR 编号冲突

**症状**：`017-SSH连接层架构设计.md` 实际上是 ADR-011（Phase 3 的 SSH 决策），但被错误编号为 017。

**根因**：创建 ADR 时没有检查 `adrs.md` 列表中已存在的编号，跳过了 011-016 直接用了 017。

**修复**：
```bash
# 1. 确认真实编号（通过 git log 或内容比对）
# 2. 重命名文件
mv "017-SSH连接层架构设计.md" "011-SSH连接层架构设计.md"
# 3. 更新文件内标题
# 4. 更新 adrs.md 索引
# 5. grep 检查所有引用
```

**预防**：
- 创建 ADR 前先读取 `docs/adrs.md` 检查最大编号
- 使用 `adrs-manager skill` 自动管理编号
- 不要在文件名中使用"大编号"（如直接用 Phase 编号作为 ADR 编号）

### 🟡 [Medium] Phase 编号引用遗漏

**症状**：Phase 6（密钥管理）插入后，ADR-017 中 "Phase 10 挂载功能" 没有同步更新为 "Phase 11"，导致引用不一致。

**根因**：Phase 编号位移是全局变更，但 grep 扫描不彻底，遗漏了引用链深处的文档。

**修复**：After this session's full audit — all 19 Phase references now verified correct.

**预防**：
- Phase 编号位移后执行全量 grep（见 document-management.md 扫描清单）
- 特别关注 ADR 文件中的"未来 Phase"引用
- 使用 `rg 'Phase [0-9]+' --type md` 扫描全部

### 🟡 [Medium] 短参数冲突预估不足

**症状**：Phase 5 设计时发现几乎所有短参数（a-z, A-Z）都被占用，
最终只剩 `-e` 可用。影响了 RQ-001 的设计（组合参数白名单必须手动维护）。

**根因**：没有在早期系统化跟踪参数占用情况。

**做法**：
- 在需求阶段就列出所有短参数占用量
- 维护参数占用表（如 `docs/parameters.md`）
- 新功能设计时优先考虑长参数，短参数预留

### 🟢 [Low] Worklog 命名一致性

**症状**：早期 worklog 命名格式不一致：
- `2026-05-09-Phase2-Plan-Design.md`
- `2026-05-09-Phase3-Plan-Design.md`
- `2026-05-10-Phase5-Plan-Design.md`

格式一致但后期文件加了前缀编号 `2026-05-10-`，早期 worklog 创建时没有前缀。

**预防**：无需强制统一（日期前缀足够排序），但新的 worklog 建议保持 `YY-MM-DD-标题.md` 格式。

## 三、可复用抽象

### 模式 1：三层架构的接口演进

```
Phase 1:  port/cryptor.go       ← 初始接口定义
Phase 2:  port/repository.go    ← 新增存储接口
Phase 3:  port/connector.go    ← 新增 SSH 连接接口
          port/session.go
          port/hostkey.go
Phase 5:  port/transfer.go     ← 新增文件传输接口
Phase 6:  port/keymgr.go       ← 新增密钥管理接口
```

**模式**：每 Phase 在 port 层新增一个接口组，service 层新增一个 Service 结构，infra 层新增一个子目录。

**可复用性**：这个模式适用于任何三层架构的渐进式开发。

### 模式 2：question 的分层策略

```
第一层（范围确认）："这个功能要做吗？"
  → 第二层（方案选择）："A、B、C 哪个方案？"
    → 第三层（细节定稿）："这个边界怎么处理？"
      → 第四层（确认）："最终检查，全部确认？"
```

**可复用性**：适用于任何需求澄清场景。先确认范围，再选择方案，然后细化边界。

### 模式 3：文档对齐批次策略

```
批次 1: AGENTS.md + plan.md （核心计划）
批次 2: TODO.md （任务清单）
批次 3: ADRs （架构决策，若需要）
批次 4: modules/*.md + storage.md + architecture.md （模块文档）
批次 5: requirements/ （需求状态更新）
批次 6: worklogs/ （工作报告）
批次 7: grep 全量验证
```

**可复用性**：任何设计完成后都按此批次更新文档。

### 模式 4：双仓库同步策略

```
assh-builder/                    asshv2/ (worktree)
  AGENTS.md                        （无代码）
  docs/TODO.md                     代码文件
  docs/plan.md                     build.sh
  docs/adrs/                       模块代码
  docs/modules/
```

**同步法则**：
- 分支名始终保持一致
- 设计文档变更在 assh-builder 提交
- 代码实现变更在 asshv2 提交
- tag 在两个仓库同步打
- 合并操作在两个仓库同步进行

### 模式 5：ADR 与代码的关联

每个 ADR 影响的具体代码文件应该在 "Consequences" 部分列出：

```
## Consequences
- 新增文件：asshc/infra/store/store.go, asshc/infra/store/migration.go
- 修改文件：asshc/service/server.go（新增 DB 依赖注入）
- 删除文件：asshc/infra/store/filestore.go（废弃）
```

这样在实现时可以快速定位 ADR 影响的代码范围。

## 四、决策矩阵

### 何时使用 ADR

| 变更类型 | ADR 必须 | 示例 |
|----------|----------|------|
| 第三方依赖选择 | ✅ | 选 SQLite vs Redis |
| 接口设计决策 | ✅ | 统一接口 vs 分离接口 |
| 安全方案 | ✅ | AES-CBC vs AES-GCM |
| 架构模式 | ✅ | 单体 vs 二进制拆分 |
| 命名约定 | ❌ | 文件名/包名 |
| 版本号策略 | ❌ | SemVer 格式 |
| 测试策略 | ❌ | Mock 框架选择 |

### 何时创建新文档 vs 修改已有文档

| 场景 | 操作 |
|------|------|
| 新增一个完整功能模块 | 创建 `docs/modules/<name>.md` |
| 修改已有模块的设计 | 编辑已有模块文档 |
| 新增一个架构决策 | 创建 `docs/adrs/<N>-标题.md` + 更新索引 |
| 用户提出临时需求 | 创建 `docs/requirements/RQ-<N>.md` |
| 完成一次完整设计周期 | 创建 `docs/worklogs/<date>-标题.md` |

### 何时创建子分支 vs 直接在 Phase 分支上工作

| 场景 | 操作 |
|------|------|
| 多人协作的复杂特性 | `feat/<feature>` |
| 单人完成的 Phase 设计 | 直接在 `dev/v2.0.0-phase-N` 工作 |
| Bug 修复 | `bugfix/<issue>` |
| 需要长时间开发的功能 | `feat/<feature>` |

## 五、工具使用复盘

### question 工具的最佳实践

**最佳频率**：每次 1-3 个问题，不超过 5 个。
**最佳格式**：描述场景 + 提供选项 + 明确优缺点。
**确认信号**：用户用短句回复（"选A"、"同意"、"可以"）。

### task 工具的最佳实践

**最佳粒度**：一个 task 完成一个模块或一个接口 + 实现。
**交接模式**：提供完整的接口签名 + 测试要求 + 验收标准。
**确认模式**：task 完成后即时验证编译通过。

### git 操作的最佳实践

| 操作 | 实践 |
|------|------|
| 提交消息 | Conventional Commits: `type: description` |
| 合并 | 始终使用 `--no-ff` 保留分支历史 |
| tag | `v<主>.<次>.<补丁>-phase-<N>` |
| worktree | `git worktree add asshv2 assh` |

## 七、项目特定经验

以下经验可能不完全适用于其他项目，但针对当前 assh 项目是经过验证的：

1. **pkg/sftp 的并发模型**：单文件内部由 `MaxConcurrentRequestsPerFile(64)` 控制，多文件由 goroutine pool（默认 3）控制，两者是正交的
2. **纯 Go SQLite**：`modernc.org/sqlite` 没有 CGO 依赖，跨平台编译直接生效（`GOOS=linux GOARCH=arm64 go build` 即可）
3. **二进制拆分**：`assh` 和 `assh-fs` 拆分的决策是正确的——短参数冲突问题在两个 binary 中各自独立，不存在冲突
4. **hash header vs 单独校验文件**：256B 固定 header 的方案比额外的 `.sha256` 文件更干净，文件传输完成后自动剥离
