# ADR-032: 远程服务器挂载方案选型与架构设计

## Status

accepted

## Date

2026-05-29

## Context

Phase 12 需要实现远程服务器文件系统挂载到本地的功能，支持用户像操作本地文件一样访问远程文件。

### 问题背景

1. **使用场景**：开发者需要频繁访问远程服务器上的文件（配置文件、日志、代码等）
2. **现有方案局限**：SFTP push/pull 是一次性操作，无法实时访问；交互式 SFTP 命令行体验有限
3. **跨平台需求**：需要支持 MacOS 和 Linux 两个主要开发平台

### 可选方案

| 方案 | 优点 | 缺点 | 依赖 |
|------|------|------|------|
| **A. sshfs** | 基于现有 SSH 基础设施，无需额外服务端配置 | 需要 FUSE 内核模块，性能一般 | macFUSE + sshfs |
| **B. WebDAV** | HTTP 协议，原生支持好 | 需要 WebDAV 服务端 | mount_webdav / davfs2 |
| C. SMB/CIFS | Windows 兼容性好 | 需要 Samba 服务端配置 | cifs-utils |

### 关键决策点

1. 挂载方案优先级
2. 命令归属（assh vs assh-fs）
3. 挂载信息是否持久化
4. WebDAV 服务端实现方式
5. 依赖检测策略
6. 进程生命周期管理

## Decision

### 1. 挂载方案：sshfs（P0）+ WebDAV（P1），SMB 延后

**理由**：
- sshfs 基于现有 SSH 基础设施，无需额外服务端配置，实现成本最低
- WebDAV 作为补充方案，适用于 sshfs 性能不佳的场景
- SMB 需要 Samba 服务端配置，使用场景相对较少，延后实现

### 2. 命令归属：assh-fs 二进制

**理由**：
- 挂载是文件系统操作，与现有 push/pull/sftp 功能职责一致
- 复用 assh-fs 的 SSH 连接和服务器管理基础设施
- 保持 assh 主二进制的简洁性

### 3. 挂载持久化：SQLite mounts 表

**理由**：
- 支持 `assh-fs mount list` 查询当前挂载
- 为未来自动挂载恢复功能奠定基础
- 与现有 SQLite 存储架构一致

**表结构**：
```sql
CREATE TABLE IF NOT EXISTS mounts (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    server_name   TEXT NOT NULL,
    remote_path   TEXT NOT NULL,
    mount_point   TEXT NOT NULL UNIQUE,
    mount_type    TEXT NOT NULL CHECK(mount_type IN ('sshfs', 'webdav')),
    local_port    INTEGER DEFAULT 0,
    daemon        INTEGER DEFAULT 0,
    pid           INTEGER DEFAULT 0,
    options       TEXT DEFAULT '{}',
    created_at    TEXT DEFAULT (datetime('now')),
    updated_at    TEXT DEFAULT (datetime('now'))
);
```

### 4. WebDAV 实现：Go 内置服务端 + SSH 隧道

**架构**：
```
本地客户端:
  mount_webdav/davfs2 → localhost:<auto-port> → Go WebDAV Server → SSH 隧道 → 远程 SFTP

远程服务器:
  SSH Server (sshd) → SFTP Subsystem → 文件系统
```

**理由**：
- 无需远程安装额外服务（如 rclone serve webdav）
- Go 实现的 WebDAV 服务端可控性高
- SSH 隧道复用现有 SSH 连接，安全性有保障

**端口管理**：
- 自动选择可用端口（18000-18999 范围）
- 多服务器挂载时避免端口冲突

### 5. 依赖检测：自动检测 + 安装提示

**MacOS**：
- 检测 macFUSE：`/Library/Filesystems/macfuse.fs` 是否存在
- 检测 sshfs：`which sshfs`
- 安装提示：`brew install --cask macfuse && brew install sshfs`

**Linux**：
- 检测 sshfs：`which sshfs`
- 安装提示：`sudo apt install sshfs`

**WebDAV**：
- MacOS：检测 `mount_webdav`（原生支持）
- Linux：检测 `mount.davfs`，安装提示 `sudo apt install davfs2`

### 6. sshfs 自动重连：默认开启

**参数**：
```bash
-o reconnect
-o ServerAliveInterval=15    # 15 秒心跳
-o ServerAliveCountMax=3     # 3 次失败后断开
-o ConnectTimeout=10         # 连接超时 10 秒
```

**理由**：
- 网络波动时自动恢复连接
- 减少用户手动重新挂载的次数

### 7. 进程生命周期：前台 + --daemon 可选

**前台模式**（默认）：
- `assh-fs mount` 后保持前台运行
- Ctrl+C 时自动卸载
- 适合临时挂载场景

**后台模式**：
- `assh-fs mount --daemon` 后返回
- 挂载点保持，需手动 `assh-fs umount`
- 适合长期挂载场景

### 8. 其他决策

| 决策项 | 结论 | 理由 |
|--------|------|------|
| 挂载点路径 | 必须手动指定 | 避免路径歧义 |
| 并发挂载 | 支持多服务器 | 实际使用场景需求 |
| 密码认证 | 优先密钥，密码时提示输入 | sshfs 不直接支持密码参数 |

## Consequences

### 正面影响

1. **与现有基础设施无缝整合**：sshfs 复用 SSH 连接，无需额外配置
2. **用户体验提升**：挂载后可直接用 Finder/文件管理器访问远程文件
3. **可扩展性**：mounts 表为未来自动恢复功能奠定基础
4. **降低使用门槛**：自动依赖检测 + 安装提示

### 负面影响

1. **WebDAV 实现复杂度高**：Go 服务端 + SSH 隧道 + 系统挂载，调试难度大
2. **MacOS macFUSE 限制**：内核扩展安装需要用户确认和重启
3. **sshfs 密码认证**：需要特殊处理（SSH_ASKPASS 或交互式输入）

### Trade-off

- **选择 sshfs + WebDAV 而非 SMB**：优先覆盖 80% 使用场景，SMB 延后
- **自动端口选择**：增加复杂度但避免多服务器冲突
- **前台 + daemon 双模式**：增加代码复杂度但提供灵活性
