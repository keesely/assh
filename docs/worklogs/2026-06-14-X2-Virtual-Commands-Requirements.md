## 需求确认过程

### 第一轮：核心功能定义

**问题**: X2 的核心功能是什么？

**用户回答**: 
- 预定义命令模板的情景是：我登录到服务器，在 tty 中输入虚拟命令
- 如果：push / pull [file] 的情况下，ssh 检测并执行相应模版命令

**关键洞察**: 
- 用户想要的是 **SSH 客户端本地命令扩展**，不是远程执行
- 虚拟命令在本地执行，不是发送到远程服务器

### 第二轮：触发机制

**问题**: 如何触发虚拟命令？

**用户回答**: 
- 前缀触发：使用 `@` 作为前缀
- 例如：`@push file`, `@pull file`

**设计决策**:
- 前缀符号：`@`
- `@command` 始终执行本地虚拟命令
- `command` 发送到远程服务器

### 第三轮：命令列表

**问题**: 需要支持哪些虚拟命令？

**用户回答**:
- `@push` - 上传文件
- `@pull` - 下载文件
- `@run` - 执行本地命令
- `@deploy` - 部署操作
- `@help` - 显示帮助
- `@version` - 显示版本
- `@status` - 显示连接状态
- `@reconnect` - 重新连接

### 第四轮：配置格式

**问题**: 虚拟命令如何配置？

**用户回答**:
- 配置文件：`~/.assh/v2/virtual.yml`
- 格式：YAML
- 作用域：全局生效
- 支持自定义命令（Shell 脚本）

**参考**: Git 的 alias 配置格式

### 第五轮：行为规格

**问题**: 错误处理、输出格式等

**用户回答**:
- 错误处理：显示错误并继续
- 输出格式：带颜色
- 命令历史：不记录
- 优先级：@push 本地优先

### 第六轮：MVP 范围

**问题**: X2 的最小可行产品包含什么？

**用户回答**:
- MVP: @push/@pull + 配置文件支持
- 技术约束：复用现有 SFTP 实现

## 需求总结

### 核心机制

1. **触发方式**: 用户在 SSH 会话中输入 `@command` 触发
2. **执行位置**: 本地执行，不是远程执行
3. **命令识别**: 前缀 `@` 明确区分虚拟命令和远程命令

### 内置命令

| 命令 | 语法 | 说明 |
|------|------|------|
| `@push` | `@push [-r] <local> [remote]` | 上传文件到远程 |
| `@pull` | `@pull [-r] <remote> [local]` | 从远程下载文件 |
| `@run` | `@run <command>` | 执行本地命令 |
| `@deploy` | `@deploy <script>` | 上传脚本并执行 |
| `@help` | `@help [command]` | 显示帮助 |
| `@version` | `@version` | 显示版本 |
| `@status` | `@status` | 显示连接状态 |
| `@reconnect` | `@reconnect` | 重新连接 |

### 配置规格

```yaml
# ~/.assh/v2/virtual.yml
virtual-commands:
  builtin:
    push:
      enabled: true
      timeout: 30s
    pull:
      enabled: true
      timeout: 30s
  custom:
    hello:
      description: "Say hello"
      script: echo "Hello!"
      timeout: 10s
  settings:
    on-error: continue
    output: color
    history: false
```

### 技术架构

```
SSH Session (tty)
    │
    ▼
Input Handler
    │
    ├── starts with '@' → Virtual Command Handler
    │                         │
    │                         ├── @push → SFTP Upload
    │                         ├── @pull → SFTP Download
    │                         ├── @run → Local Exec
    │                         └── ...
    │
    └── otherwise → Send to Remote Shell
```

### 复用组件

| 组件 | 复用方式 |
|------|----------|
| `asshc/infra/sftp/` | @push/@pull 的文件传输 |
| `asshc/infra/ssh/` | SSH 连接管理 |
| `config/` | 配置文件加载 |
| `log/` | 日志输出 |

## 关键决策

### 1. 前缀符号选择
- **决策**: 使用 `@` 作为前缀
- **理由**: 
  - 视觉上清晰
  - 不与常见 shell 语法冲突
  - 类似 Slack/Telegram 的斜杠命令

### 2. 命令作用域
- **决策**: 全局生效
- **理由**: 
  - 简化实现
  - 用户体验一致
  - 后续可扩展为按服务器/分组配置

### 3. 配置格式
- **决策**: YAML 格式
- **理由**: 
  - 用户选择
  - 可读性好
  - 支持复杂结构

### 4. 错误处理
- **决策**: 显示错误并继续
- **理由**: 
  - 保持 SSH 会话不中断
  - 用户可以看到错误信息
  - 符合交互式命令行习惯

### 5. MVP 范围
- **决策**: @push/@pull + 配置文件
- **理由**: 
  - 聚焦核心功能
  - 复用现有 SFTP 实现
  - 快速验证可行性

## 技术挑战

### 1. 输入拦截机制
- **挑战**: 如何在 SSH 会话中拦截用户输入
- **方案**: 修改 SSH 会话的输入处理逻辑
- **风险**: 可能影响正常的 SSH 交互

### 2. 命令解析
- **挑战**: 如何解析带参数的虚拟命令
- **方案**: 使用 shell 风格的参数解析
- **风险**: 参数中可能包含特殊字符

### 3. 进度显示
- **挑战**: 文件传输进度如何在 SSH 会话中显示
- **方案**: 使用 ANSI 转义码更新同一行
- **风险**: 终端兼容性问题

### 4. 超时处理
- **挑战**: 如何中断长时间运行的操作
- **方案**: 使用 context.WithTimeout
- **风险**: 某些操作可能无法优雅中断
