# PM Agent 工作流方法论

> 适用于产品经理（PM） Agent 在项目开发中的工作流程、决策模型和最佳实践。
> 基于 assh v2.0.0 项目 Phase 4 开发实践总结提炼。

---

## 一、工作流全景

```
需求触发
   │
   ▼
┌──────────────────────────────────────────────────────┐
│              1. 需求澄清与边界定义                     │
│  question / webfetch / 对话 逐项确认需求               │
│  输出: 明确的验收标准 + 变更范围                        │
└──────────────────────────────────────────────────────┘
   │
   ▼
┌──────────────────────────────────────────────────────┐
│              2. 现状分析与差异对比                     │
│  read / grep / glob 查阅代码和文档                    │
│  对比 v1/v2、定义 vs 实现、预期 vs 实际                │
│  输出: 差异报告 / 差距分析                             │
└──────────────────────────────────────────────────────┘
   │
   ▼
┌──────────────────────────────────────────────────────┐
│              3. 方案确认（逐项决策）                   │
│  将差异点拆解为独立议题 → 逐项与用户确认方向            │
│  输出: 确定的实施方案（列结构 / 行为 / 参数表）         │
└──────────────────────────────────────────────────────┘
   │
   ▼
┌──────────────────────────────────────────────────────┐
│              4. 架构决策记录（ADR）                    │
│  触发条件检查 → 创建 ADR → 更新索引 → 状态流转         │
│  工具: adr-cli.py / Markdown                         │
│  输出: ADR-XXX.md + adrs.md 索引更新                  │
└──────────────────────────────────────────────────────┘
   │
   ▼
┌──────────────────────────────────────────────────────┐
│              5. 任务调度与执行                         │
│  task → build agent（含完整上下文 + 验证命令）          │
│  跟踪执行状态，验证结果                                │
│  输出: 代码变更 + 编译/测试通过                       │
└──────────────────────────────────────────────────────┘
   │
   ▼
┌──────────────────────────────────────────────────────┐
│              6. 文档对齐                             │
│  同步更新 AGENTS.md / TODO.md / plan.md             │
│  更新 worklogs / bugs / adrs 等关联文档              │
│  输出: 所有文档状态一致                              │
└──────────────────────────────────────────────────────┘
   │
   ▼
┌──────────────────────────────────────────────────────┐
│              7. 版本管理                             │
│  提交代码 + 提交文档 → 打 tag（Phase 完成时）         │
│  git commit + push + tag / git-manager skill         │
│  输出: 干净的提交历史 + 版本标记                      │
└──────────────────────────────────────────────────────┘
```

## 零、自动编译检查（新规）

> 每次执行变更或 bugfix 后（无论 PM Agent 直接编辑还是调度 build agent 执行），**必须自动执行编译检查**：
> ```
> cd asshv2 && go build ./...
> ```
> 编译未通过则不得进入下一步（提交/合并/文档对齐）。

**例外**：
- 仅修改纯文档（如 `*.md`、`AGENTS.md`）且不涉及代码逻辑的，可跳过编译检查
- 编译命令修改为 `go build ./...`（全包构建，捕获跨包依赖错误）

**工作流融合**：
- PM Agent 直接编辑 `cmd/` 等代码文件 → 编辑完成后立即编译
- 调度 build agent → 在 task 上下文中包含编译验证命令
- 质量门禁中的编译检查保持为最终通过的确认步骤

## 二、各阶段详解

### 1. 需求澄清与边界定义

**触发时机**：用户提出需求、变更、bug 报告时。

**核心原则**：
- 将模糊描述拆解为具体的、可验证的条目
- 使用问题逐项确认，**避免一次性提出全部问题**
- 确保所有争议完全消除，边界完全明确

**输入/输出**：

| 输入 | 输出 |
|:-----|:-----|
| 用户原始描述（可能模糊） | 明确的验收标准清单 |
| 截图/示例 | 变更范围界定 |
| 问题列表 | 排除不在范围内的需求 |

**技巧**：
- 用 `question` 工具（不可用时直接用对话）逐项确认
- 先确认"要不要改"，再确认"改成什么样"
- 用"议题 X：..."格式将复杂问题拆解

**示例**（来自 Phase 4 ls 视图修正）：
```
议题 1：Remark 列 — 是否加回？
  A. 不加   B. 加回
→ 用户选 B

议题 2：列位置
  A. 最后一列   B. Name 之后
→ 用户选 A
```

---

### 2. 现状分析与差异对比

**触发时机**：需求涉及与旧版本/原有设计的对比时。

**方法**：
- 并行读取：同时读取新旧代码，减少往返
- 对照检查：逐项对比定义与实际
- 表格化输出：用 Markdown 表格呈现差异

**对比维度**：

| 维度 | 适用场景 | 示例 |
|:-----|:---------|:-----|
| 命令结构 | CLI 变更 | v1 21 个扁平命令 vs v2 5 个命令+子命令 |
| 参数列表 | 参数对齐 | `-R`(v1) vs `--remark`(v2) |
| 输出格式 | 视图调整 | ls 4 列 vs 7 列 |
| 行为模式 | 默认行为 | 显式 login vs 默认登录 |
| 架构约束 | 依赖注入 | service 是否直接依赖 infra |

**输出**：差异报告（Markdown 表格），包含：
- 差异项
- v1 做法
- v2 做法
- 评价/建议

---

### 3. 方案确认（逐项决策）

**核心原则**：一次只确认一个议题，避免混淆。

**流程**：
```
1. 列出所有差异点 → 用户确认差异清单
2. 对每个差异点提出选项（A/B）→ 用户选择
3. 确认细节（位置、宽度、颜色等）→ 用户选定
4. 汇总最终方案 → 用户确认
```

**技巧**：
- 选项不宜过多（最好 2-3 个）
- 每个议题确认后立即记录（如用 todowrite 标记）
- 复杂方案用示例输出直观展示

---

### 4. 架构决策记录（ADR）

**触发条件检查**（任意一项成立则必须创建）：

| 条件 | 本次示例 |
|:-----|:---------|
| 🔴 新技术栈引入 | 无 |
| 🔴 不兼容变更 | ADR-014：server 命令从子命令变为顶层 |
| 🔴 架构模式调整 | ADR-015：ls 输出结构 + 颜色方案 |
| 🟡 安全与合规 | 无 |
| 🟡 核心流程重构 | ADR-016：默认登录行为变更 |

**创建流程**：
```
1. adr-cli.py new "标题" --workspace <name> --context ... --decision ... --consequences ...
2. adr-cli.py status <id> accepted
3. 创建 Markdown 文件 docs/adrs/XXX-标题.md（修正格式）
4. 更新 docs/adrs.md 索引（统计 + 列表 + Phase 摘要）
5. 提交文档
```

**ADR 编号策略**：
- 文件编号 = 连续数字（001-013, 014, 015...）
- 工具编号（SQLite ID）用于内部管理
- 索引表中使用文件编号

---

### 5. 任务调度与执行

**原则**：PM Agent 不直接写代码，调度 build agent 执行。

**调度前准备**：
- 完整的变更加上下文
- 清晰的修改要点（改什么、怎么改）
- 验证命令（build / vet / test / 行为测试）

**task 指令结构**：

```
## 任务
背景...（为什么改）

## 修改要点
1. 文件 A：改什么
2. 文件 B：改什么

## 实现细节
代码示例/关键逻辑

## 验证
go build ./...
go vet ./...
go test ./...
go run . <test-command>
```

**执行后检查**：
- ✅ 编译通过
- ✅ 静态检查通过
- ✅ 测试通过
- ✅ 行为验证通过
- ⚠️ 任何注意事项

---

### 6. 文档对齐

**对齐清单**（每次设计/架构变更后执行）：

| 文档 | 检查点 |
|:-----|:--------|
| `AGENTS.md` | 阶段状态、已完成模块、技术栈 |
| `docs/TODO.md` | 任务状态、Phase 描述 |
| `docs/plan.md` | 项目结构、功能列表 |
| `docs/architecture.md` | 架构图、数据流 |
| `docs/storage.md` | 存储路径、数据库结构 |
| `docs/constraints.md` | 依赖列表 |
| `docs/adrs.md` | 索引更新 |
| `docs/adrs/XXX-*.md` | 文件创建 |
| `docs/worklogs/` | 工作报告 |
| `docs/bugs/` | Bug 记录（如有） |

---

### 7. 版本管理

**提交策略**：
- 代码变更 + 文档变更分开提交
- 提交信息格式：`type: description (reference)`
- 示例：`feat: add default login action for v1 compatibility per ADR-016`
- 示例：`fix: manual short flag parsing for default login action (v1 compat)`
- 示例：`docs: add ADR-016 for default login action`

**分支管理**：
- 从 `master` 创建 `dev/vx.x.x-phase-N` 分支
- 特性/修复从 Phase 分支拉出
- Phase 完成后 PR → master + 打 tag

## 三、决策树模型

```
用户提出需求
   │
   ├── 是需求澄清？ → Step 1：逐项确认边界
   │
   ├── 需对比分析？ → Step 2：差异报告
   │                     │
   │                     ▼
   │                  Step 3：逐项确认方案
   │
   ├── 涉及架构变更？ → Step 4：ADR
   │
   ├── 需要代码修改？ → Step 5：调度 build agent
   │
   ├── 文档需要更新？ → Step 6：文档对齐
   │
   └── 需要提交代码？ → Step 7：版本管理
```

## 四、工具链映射

| 步骤 | 主要工具 | 辅助工具 |
|:-----|:---------|:---------|
| 需求澄清 | 对话/question | todowrite（记录决定） |
| 差异分析 | read / grep / glob | bash（编译/运行对比） |
| 方案确认 | 对话（逐项） | todowrite（记录进度） |
| ADR 记录 | bash（adr-cli.py） | write（Markdown 文件） |
| 任务调度 | task（general agent） | — |
| 文档对齐 | read / write / edit | glob（发现遗漏） |
| 版本管理 | bash（git） | git-manager skill |
| Bug 追踪 | write / edit | bash（git commit） |

## 五、最佳实践

### 5.1 工作习惯

1. **并行化** — 独立的任务并行执行（如同时读取多个文件）
2. **小步提交** — 代码/文档变更分开提交，语义清晰
3. **每次变更一个主题** — 避免混合同一次提交多个无关功能
4. **先记录后执行** — 架构决策先写 ADR，再调度执行
5. **验证驱动** — 任何修改必须附带验证命令

### 5.2 沟通习惯

1. **一次一个议题** — 议题拆解到最小可决策单元
2. **提供选项** — 给用户 A/B 选项而非开放性问题
3. **确认后立即记录** — 避免上下文丢失
4. **最终汇总** — 所有议题确认后汇总最终方案，请用户确认

### 5.3 文档习惯

1. **ADR 先行** — 架构变更先记录再实施
2. **查漏补缺** — 每次变更后执行文档对齐清单
3. **工作报告** — 完整的工作记录（分析/设计/决策/执行全过程）
4. **Bug 留痕** — 每个 bug 记录根因和解决方案，不仅是修复代码

### 5.4 避免的陷阱

| 陷阱 | 后果 | 对策 |
|:-----|:------|:------|
| 一次性确认过多议题 | 用户决策疲劳，细节遗漏 | 拆解为最小单元，逐项确认 |
| 跳过 ADR 直接改代码 | 决策上下文丢失，日后难以追溯 | 架构/行为变更必须先 ADR |
| 文档滞后于代码 | 文档与代码不一致 | 变更完成后立即执行文档对齐 |
| task 上下文不足 | build agent 理解偏差，反复返工 | 提供完整的背景 + 修改要点 + 验证命令 |
| 忽略 urfave/cli 框架行为 | 产出与预期不符的 bug | 关键框架行为先用最小示例验证 |

## 六、质量门禁

每次变更完成验收前，必须通过以下检查：

```
□ 编译通过      go build ./...
□ 静态检查通过   go vet ./...
□ 单元测试通过   go test ./... -count=1
□ 行为验证通过   实际运行验证（至少一个正向用例）
□ ADR 已记录    如涉及架构变更
□ 文档已对齐    见文档对齐清单
□ Bug 已记录    如有修复
□ 代码已提交    git commit（含清晰的提交信息）
```
